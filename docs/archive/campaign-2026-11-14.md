# Campagne du 14 novembre 2026 : garanties, stabilisation, coût

> Archived 2026-11-15: measured with `cmd/benchmark` and `scripts/local/campaign.py`
> on the bbolt store. Both are archived outside the repository with the load
> harness; the numbers explain [linear-knowledge.md](../protocol/linear-knowledge.md).

Les garanties ont tenu partout : 0 erreur d'audit, 0 erreur inattendue et
aucun run classé `bug` sur 42 runs avec écritures (18 `orig`, 24 `new`), et
42 exécutions de scénarios réseau adversariaux sur 42. Le coût
du plan de contrôle, lui, ne tient pas l'échelle : pendant les splits, le débit
chute de 80 % ; l'amorçage croît en N^2,8. La cause mesurée est le décodage du
document de contrôle `causal-v1`.

Comparaison A/B sur les mêmes graines : `orig` est le code au commit `08e1e95`,
`new` y ajoute l'index d'autorité, la mémoïsation de la réplique, les
activations sans frontier et la reconnaissance des faits sans hachage. Voir
[linear-knowledge.md](../protocol/linear-knowledge.md).

## Conditions

- Conteneur Linux, 2 CPU, Go 1.24 avec `sync.WaitGroup.Go` rétroporté ; le
  `go.mod` du dépôt demande 1.26. L'adaptateur HTTP/3 n'est pas couvert.
- Banc `cmd/benchmark` : vrai `mesh.Service`, Bolt, transport en mémoire, un
  vnode par nœud, tous sur la même machine. Ce ne sont pas des mesures réseau.
- `durable-batch` synchronise le disque : ce conteneur plafonne alors vers 140
  écritures/s. Les scénarios à splits utilisent `logical-batch` (mêmes règles,
  sans `fsync`), qui tient au moins 1 500 écritures/s sans split.
- Commande : `scripts/local/campaign.py run --seeds 22,23 orig=... new=...`.

## Comportements observés

**Splits sous charge.** Sans split, 1 500 écritures/s passent. Dès deux splits,
quatre transferts restent ouverts environ 95 s, deux vues coexistent, le débit
tombe à 50–400/s et la file déborde. Chaque nouveau vnode met de 60 à 100 s à
couvrir sa cellule. Les deux versions se comportent ainsi.

**Point chaud atomique.** Le split est refusé trois fois (`no safe fork`), sans
effet de bord (HOT-2). Un vnode garde 82 % des lignes ; le débit reste à
800/s avec un p95 de 6 ms. Seul un découpage plus fin des locations dans le
modèle de données peut répartir cette charge.

**Amorçage séquentiel** (charge négligeable) :

| Vnodes | orig | new |
| --- | --- | --- |
| 16 | 1,7 s | 1,5 s |
| 32 | 11,8 s | 10,3 s |
| 48 | 76 s | 49 s |
| 64 | 127 s | 69 s |

À 64 vnodes, le scénario chargé dépasse son budget d'amorçage de 180 s dans les
deux versions (`inconclusive`, aucune écriture).

**Connaissance transportée** : environ 6 Ko par vnode à 32 vnodes, certificats
compris ; elle ne domine plus aucun profil.

## Où part le temps

Profils CPU pris avec `-cpuprofile` :

| Situation | Premier poste | Part |
| --- | --- | --- |
| Splits sous charge, avant correction | JSON : `Marshal` 32 %, `Unmarshal` 25 % ; empreintes de `ZoneTransfer` 15 % ; revérification des bundles 15 % | — |
| Splits sous charge, après | `readCausalControl` (décodage de `causal-v1`) | 25 % |
| Amorçage à 48 vnodes | `readCausalControl` | 67 % |

Corrigé dans cette passe, sans changement de règle ni de format : les
`ZoneTransfer` connus sont reconnus par valeur (15 % → 1,75 %), et un bundle
dont la version a déjà été vérifiée n'est ni réencodé ni refusionné. Gain : +17 %
de débit pendant les splits sur le même scénario.

Reste à faire : `causal-v1` contient tout l'historique des transferts du nœud,
terminés compris, et il est décodé en entier à chaque `CausalState()`. Le
découper en une clé par fait et par transfert (étape E5) est la prochaine
linéarisation ; c'est un changement de format persistant.

## Limites

- Une machine, 2 CPU : les durées absolues ne valent que pour la comparaison.
- Deux graines par scénario de charge ; une seule pour `vnodes-32` et
  l'amorçage.
- Les deux tests de débit extrême du paquet `benchmark` dépassent leurs délais
  sur cette machine : deux échecs sur deux pour `orig`, un ou deux selon le run
  pour `new`. Aucune garantie n'y est violée (audit vide, 0 ligne volée).
